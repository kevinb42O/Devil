# Online friends mode

Open **Friends · up to 6 players**. Everyone loads the same public game URL.

1. Enter your player name.
2. Click **Create lobby**, or click **Join** on a visible lobby in **Open lobbies**.
3. Creating or joining places you directly in the shared courtyard. Friends can keep joining while you hang out. Copy an invite from **Room & crew** or the courtyard toolbar; invite URLs join that room directly.
4. The right-hand passage leads to a separate football room with a 36 × 50-meter textured pitch and two nine-meter netted goals. Hold left mouse to charge a left-foot kick and release to strike the original in-game skull; full power takes 1.2 seconds, and right mouse cancels. A ball fully outside the pitch returns to exact midfield, preserving the score. Charge, contact, and kick strength are host-authoritative; the left-leg pose is shared with the crew. You can also high-five. The football skull has dedicated courtyard lighting; both goal scoreboards show the same shared score, and a goal whistle plays once for each confirmed goal. Combat skull rendering and audio remain unchanged. Press F to ready/unready on keyboard; tap Ready up on mobile. Colors and eligible skins can be changed while gathering; changing appearance clears your ready status.
5. Each player finishes loading and marks ready. When all current players are present and ready, and the pit cover is clear, only the host can hold **Open pit**.
6. The cover slides open. Every player drops into the shaft; the host starts one synchronized arena epoch only when everyone is below. The existing one-second settling interval and five-second arrival countdown precede survival simulation.
7. The host can cancel departure. Unreadying or a lost connection before launch also restores dropped players before closing the cover. Empty slots never block a smaller crew.
8. After the crew falls, the host selects **Return to courtyard**. Ready state, pit, social effects and skull reset; the last descent and current crew's best remain visible. Full results and team replays remain accessible through the existing results/history flow.

Lobby discovery and connection negotiation use public internet signaling. Gameplay uses WebRTC between the host browser and up to five guest browsers. Gathering rooms remain joinable; opening the pit freezes admissions until the next courtyard. Host migration and joining an arena run already in progress are not supported.

The courtyard uses the existing authored skull mesh/texture and floor tiles. Its additional CC0 props are downloaded Kenney models, stored locally with embedded palette textures; see `public/models/courtyard/LICENSE.md` and `assets/provenance/courtyard/`. `python3 tools/import-courtyard-assets.py` reproduces those prop imports. No generated model is used.

## Shared gems

Any player collecting one gem gives **every player +1 gem**. Gem progression is identical across the lobby. Hands unlock at 10, 70 and 200 total shared gems; spending homing ammunition cannot delay the final hand. Homing unlocks with hand II at 10 collected gems; each subsequent gem adds one homing dagger to every player’s individual reserve. Right mouse button or controller LT/L2 fires homing. The sword counter beside collected gems shows the local player’s remaining ammo. Each player has their own weapon cooldowns and homing reserve; spending homing ammunition does not spend another player's reserve. The same gem cannot be collected twice.

Living teammates use simple colored bodies with subtle names above their heads. Their daggers and muzzle particles are visible to the crew; teammate firing never recoils your own hand. The in-game roster uses player names. Local movement, jumping, firing and dagger jumps are predicted immediately using the shared controller. Host snapshots acknowledge numbered input commands, restore authoritative controller state and replay outstanding commands. Damage, collection, progression, death and respawning remain authoritative on the host.

Input commands represent individual 120 Hz ticks, preserving press/release timing and held durations. Unchanged samples are run-length encoded on the wire and expanded into individual ticks on the host, reducing input traffic without compressing held durations. Outstanding commands are retransmitted over an unordered WebRTC channel and deduplicated by sequence number. Input history is bounded to two seconds. The host reports its queued command count; guests briefly pace input generation when more than six commands are queued, draining lag-spike backlogs without dropping queued ticks/taps or granting extra movement ticks. During recovery, movement-only input is sampled at 75% rate (50% for queues over 60 ticks). Primary/homing holds, jump input and their release ticks always retain full 120 Hz sampling, so recovery cannot change tap/stream classification, fire output or jump edges. A backlog drains during movement-only periods; continuous firing keeps its original timing. Button edges stay queued until prediction accepts them. Prediction stops after one second without a snapshot or 500 ms without an advancing host tick once the countdown has elapsed. Losing focus or mouse capture sends an immediate reliable release of outstanding controls without pausing. Release and timeout handling preserve the last processed yaw/pitch, including bursts completed by that release. Countdown deadlines are mapped from the host clock into the guest clock, so a different system clock cannot block gameplay. Connection offers reject incompatible protocol versions with an explicit reload message.

World updates use a separate unordered binary channel. Enemy updates reuse acknowledged baselines: positions use a 1/512-unit presentation grid and packed residuals, age advances locally, and metadata updates contain only changed fields. Velocity uses the same 1/512 grid; phase and facing angles use 1/1024 radians. Health, damage timestamps, rig segments and weakpoints retain float32 precision. Pose coordinates are quantized before float32 conversion, and both peers retain that exact canonical wire position in their baseline. This prevents drift at float32/grid rounding boundaries. Metadata residuals also quantize both baseline and destination. Authoritative simulation and player controller values are never quantized. Every update includes the complete active enemy ID list, preserving removals after packet loss. Ordinary multi-dagger shots send a seed, aim/hand transform and the identities/indices of surviving daggers; clients reconstruct the exact spread with the shared launch function. Small shots and modified, homing or bounced trajectories use explicit projectile updates. Active ID lists use packed signed varints. Projectile spawns and trajectory changes are sent relative to acknowledged snapshots; ordinary flight and gravity after a bounce are reconstructed between updates. Every update includes the complete active projectile ID list, so a lost removal cannot leave permanent daggers. Missing baselines trigger a self-contained recovery update. Fragmented updates allow overlapping frames and include one repair chunk per eight data chunks to recover isolated loss. Frames up to 64 KiB expire after 300 ms; larger frames have a transfer window sized for 32 KB/s with startup slack, capped at ten seconds. Memory remains bounded to four incomplete frames. State traffic has a 192 KB/s state budget per guest (about 1.5 Mbps) with a bounded startup/recovery burst. Playing frames send at most eight chunks per pump, charge each chunk to the budget, respect channel backpressure and retain at most one immutable outgoing frame per peer. Frames exceeding the 256 KiB token bucket can therefore finish across pumps. An immutable baseline candidate is cached before transmission; only a receiver ACK makes it a delta base, including when the receiver finishes before trailing repair packets. Epoch changes and lobby returns cancel old transfers. Lifecycle messages and deduplicated effects use the reliable control channel. Effects flush independently of snapshot budget/congestion after lifecycle state establishes the epoch; failed sends retain queued effects.

Guests interpolate remote enemies, gems and teammates using an adaptive 50–200 ms presentation buffer. Their own camera uses the predicted controller, with short smoothing for small authoritative corrections and immediate correction for large errors or death. Network transmission runs on a wall-clock timer independently of rendering. Host simulation uses a shared fixed-step clock driven by render frames and worker wake-ups; suspending rendering does not stop its clock, and overlapping wake-ups cannot double-simulate elapsed time. Only one worker wake-up may be in flight; long suspensions cap catch-up work at 30 ticks. Diagnostics also report authoritative tick stalls and the guest host-queue depth. Prediction, the waiting HUD and the connection meter share the same waiting-for-host condition, including an advancing-tick timeout. The development diagnostic surface includes round-trip latency, snapshot age, outstanding commands, correction distance, interpolation delay, traffic rates, update frequency, host simulation cost and queued bytes.

Players have individual lives. The shared arena continues after an individual death or guest disconnect. Eliminated players spectate with an independent free-flying camera: mouse to look, WASD to fly in the viewing direction, Space/E to rise, Ctrl/Q to descend, and Shift to fly faster. Flight stays within a fixed 50-unit bubble centered above the arena, with a lower limit above the floor. The camera never follows surviving teammates; spectators cannot fire or collect gems. Each death starts a 15-second countdown in host simulation time. At the deadline, the player returns beside the nearest living teammate to their death location, facing that teammate’s direction. Placement uses valid ground around the teammate, including when they are jumping; unsafe targets are skipped, and revival waits if no safe position exists. Weapon level and remaining homing reserve carry over, with shared gem progression continuing during the wait. Enemy damage is ignored for one second after revival; falling remains lethal. Spectator controls and weapon timing reset on return. Inputs are tagged with a life counter so delayed commands from before death cannot control a revived player. Disconnected players cannot respawn or anchor another player’s return. A team wipe ends the run immediately, including on a respawn deadline, and pending revivals cannot restart it. The host can return everyone to the lobby; readiness resets so everyone readies up again before the next run. If the host leaves, guests return to the lobby browser. Joining a running or full lobby is disabled.

In the courtyard, Escape opens the local pause menu without stopping other players. Room & Crew reopens the roster, and Leave exits the session. Once in the arena, multiplayer cannot be paused: Escape and controller Start / Options do nothing, and the mobile timer pause target is disabled. Play until the crew dies. Keep the host computer awake. Worker wake-ups support a backgrounded host tab, but browser or operating-system suspension can still stop execution; guests detect stalled simulation even if stale snapshots continue arriving. Browsers may require a click to recapture the mouse after switching windows, even though the game and timer start for everyone.

## Online hosting

`npm run build` produces the static game in `dist/`. `npm run serve:online` serves only that directory on localhost port 5180, with compression for scripts, meshes, styles and JSON. Publish this service through an HTTPS tunnel for a temporary playtest, or upload `dist/` to an HTTPS static host for a persistent URL. Everyone opens the resulting **internet URL**, then uses the lobby browser.

Lobby discovery uses public MQTT brokers with failover, separate room and lobby namespaces, heartbeat announcements and stale-room expiry. Ready state and start authority travel over reliable WebRTC channels; the host validates every readiness transition and will not start a public lobby with unready players. Only the host can open the central pit after everyone has loaded and readied up. The arena begins once every crew member has dropped into the open pit; the host validates each descent. Peer IDs are validated before signaling creates offers or roster entries, and again when parsing connection codes or routing inputs. Reserved host IDs and malformed IDs cannot enter the lobby or overwrite host controls. Ready/unready controls carry monotonic revisions; local intent updates immediately and stale roster snapshots cannot undo a newer click.

Room signaling forwards ICE candidates discovered after the initial seven-second SDP gathering window, queues candidates until the remote description is available, and replays them on handshake retries. Duplicate broker deliveries apply each candidate once. A guest waiting for the first host roster sees Connecting, with Ready enabled once their roster entry arrives.

Direct internet connections use Google and Cloudflare STUN. Deployments that need relay fallback can configure `VITE_WEBRTC_ICE_SERVERS` with their own ICE server JSON before building. This is deployment configuration; players never enter network settings in the game. A TURN relay account is not bundled. Different-home NAT traversal still depends on the participating networks; testing several browser profiles on one computer does not establish compatibility with every firewall.

## Validation

- `npm run test:lobby-joining`: isolated-broker discovery, lost offer/answer recovery, delayed and dropped ICE candidates, candidate deduplication, and a phone-sized touch Ready flow (requires a running development build).

- `npm test`: solo regression tests plus crew movement/deaths, shared gem credit, independent homing reserves and snapshot application.
- `npm run test:multiplayer`: six real WebRTC clients exercising the courtyard, host pit hold, shared descent, arena fire, wipe, return and disconnect; discovery is stubbed.
- `npm run test:courtyard`: courtyard state/physics/prediction, charged football kicks and boundary resets, plus two-client UI flow and mobile/controller checks.
- `npm run test:football-feedback`: football illumination, unchanged combat skull pixels, synchronized score displays, goal audio and left-leg pose checks.
- `npm run test:courtyard:six`: ten six-client courtyard/run/return cycles.
- `GAME_URL=http://127.0.0.1:4173 node tests/courtyard-invite-browser.mjs`: production UI, actual public signaling, copied invite URLs, automatic joining, host pit controls and departure. Start the production preview first. All browser checks require a running development server; set `GAME_URL` to use another address.
- `npm run test:multiplayer-respawn`: respawn rules and a real WebRTC 15-second guest countdown, camera return, held-input cleanup, fresh movement/firing, host revival, repeated death, wipe and restart (requires a running development build; public discovery is stubbed).
- `npm run test:multiplayer-spectator`: spectator flow and revival with AZERTY, controller and mobile controls.
- `npm run test:multiplayer-transport`: real WebRTC input, large fragmented snapshots, epoch changes and a complete guest tap received before simulation.
- `npm run test:multiplayer-recovery`: backlog drainage, retained button edges, aim-preserving releases/timeouts, stalled-tick detection, seed reconstruction, immutable baselines, quantization drift bounds and actual host simulation with rendering suspended.
- `npm run test:multiplayer-network-regressions`: physical primary/homing hold timing under recovery, rounding-boundary baselines through loss/keyframes/far poses, budgeted medium/large transfers, backpressure, early ACKs, effects independent of congestion, identity validation and unified stall status; includes real WebRTC transfer of 6,000 projectiles, early reliable effects and restart cancellation.
- `npm run test:multiplayer-soak`: 15 seconds of four-player level-IV firing/movement over real WebRTC with 120 ms added RTT, 20% input loss, reordering, isolated snapshot loss and a 250 ms input blackout; verifies full acknowledgement recovery, bounded queues, stopped firing and matching final positions.
- `npm run test:multiplayer-latency`: immediate predicted movement/burst/dagger jump, real WebRTC with 60 ms delay in each direction, dropped/reordered input datagrams, lost state chunks, acknowledgement recovery and epoch reset (requires internet access for the production STUN configuration).
- `npm run test:multiplayer-pause`: keyboard, controller and mobile pause prevention, focus/capture loss, controller disconnect, continuous timer and normal death (runs without internet discovery).
- `npm run test:multiplayer-responsiveness`: actual game keyboard input and rendered camera response on the next frame with 1,000 ms added RTT, plus focus-loss release recovery (requires internet lobby discovery).
- `npm run test:multiplayer-presentation`: teammate labels, remote muzzle particles without local recoil, local recoil, death visibility and cleanup.

Current scope includes up to six players, a joinable social courtyard, readiness and host-controlled pit, synchronized arena arrival, individual movement/weapons/deaths, shared gem rewards and recorded team replays. No host migration or mid-run admission. Multiplayer scores remain separate from solo records.

The deterministic four-player level-IV firing benchmark in `tests/network.test.ts` measures approximately 80 KB/s of state per guest, including repair chunks, versus approximately 2.5 MB/s with escaped full-world JSON over the same two-second run. This is an empty-arena state benchmark, not a guarantee for dense endgame encounters; homing, enemies, reliable effects, input retransmission and transport headers add traffic. The network tests also cover landing/weapon-state reconciliation, independent shot randomness, lost baselines, removals, corrupted packets and fragment expiry. All players must reload the updated build before playing together.

The 1,000-enemy pose benchmark reduces steady-state enemy updates from approximately 78 KB to 5 KB per snapshot before repair chunks; health changes and removals are verified against decoded state. Browser interruptions release held guest controls while the match continues. Late releases are ignored after newer commands have been processed, critical releases remain deliverable under control-channel pressure, and run restarts discard old queued effects and baselines.

The optimized pose-only 1,000-enemy benchmark includes approximately 126 KB/s at 20 Hz with repair chunks, down from approximately 348 KB/s before the packed residual format. These are controlled benchmarks; changing enemy metadata and projectile corrections add traffic. Network protocol version 13 requires every player to reload the same build.
