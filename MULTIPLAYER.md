# Online friends mode

Open **Friends · up to 4 players**. Everyone loads the same public game URL.

1. Enter your player name.
2. Click **Create lobby**, or click **Join** on a visible lobby in **Open lobbies**.
3. Each player clicks **I'm ready**. Player cards show everyone's readiness.
4. When every connected player is ready, the host's **Start run** button becomes available.
5. The host starts a shared three-second countdown. All players enter the same run.

There are no room-code fields, copied connection offers, or LAN setup in the game interface. Lobby discovery and connection negotiation use public internet signaling. Gameplay uses WebRTC between the host browser and up to three guest browsers.

## Shared gems

Any player collecting one gem gives **every player +1 gem**. Gem progression is identical across the lobby. Hands unlock at 10, 70 and 200 total shared gems; spending homing ammunition cannot delay the final hand. Homing unlocks with hand II at 10 collected gems; each subsequent gem adds one homing dagger to every player’s individual reserve. Right mouse button or controller LT/L2 fires homing. The sword counter beside collected gems shows the local player’s remaining ammo. Each player has their own weapon cooldowns and homing reserve; spending homing ammunition does not spend another player's reserve. The same gem cannot be collected twice.

Living teammates use simple colored bodies with subtle names above their heads. Their daggers and muzzle particles are visible to the crew; teammate firing never recoils your own hand. The in-game roster uses player names. Local movement, jumping, firing and dagger jumps are predicted immediately using the shared controller. Host snapshots acknowledge numbered input commands, restore authoritative controller state and replay outstanding commands. Damage, collection, progression, death and respawning remain authoritative on the host.

Input commands represent individual 120 Hz ticks, preserving press/release timing and held durations. Unchanged samples are run-length encoded on the wire and expanded into individual ticks on the host, reducing input traffic without compressing held durations. Outstanding commands are retransmitted over an unordered WebRTC channel and deduplicated by sequence number. Input history is bounded to two seconds; prediction stops after one second without a host snapshot. Losing focus or mouse capture sends an immediate reliable release of outstanding controls without pausing. Countdown deadlines are mapped from the host clock into the guest clock, so a different system clock cannot block gameplay. Connection offers reject incompatible protocol versions with an explicit reload message.

World updates use a separate unordered binary channel. Enemy updates reuse acknowledged baselines: positions and advancing age are compact, while changed health, kind, status, rig segments and weakpoints trigger complete enemy records. Every update includes the complete active enemy ID list, preserving removals after packet loss. Projectile spawns and trajectory changes are sent relative to acknowledged snapshots; ordinary flight and gravity after a bounce are reconstructed between updates. Every update includes the complete active projectile ID list, so a lost removal cannot leave permanent daggers. Missing baselines trigger a self-contained recovery update. Fragmented updates expire after 300 ms, allow overlapping frames, and include one repair chunk per eight data chunks to recover isolated loss. State traffic has a 192 KB/s state budget per guest (about 1.5 Mbps) with a bounded startup/recovery burst. Lifecycle messages and deduplicated effects use the reliable control channel.

Guests interpolate remote enemies, gems and teammates using an adaptive 50–200 ms presentation buffer. Their own camera uses the predicted controller, with short smoothing for small authoritative corrections and immediate correction for large errors or death. Network transmission runs on a wall-clock timer independently of rendering. The development diagnostic surface includes round-trip latency, snapshot age, outstanding commands, correction distance, interpolation delay, traffic rates, update frequency, host simulation cost and queued bytes.

Players have individual lives. The shared arena continues after an individual death or guest disconnect. Eliminated players spectate with an independent free-flying camera: mouse to look, WASD to fly in the viewing direction, Space/E to rise, Ctrl/Q to descend, and Shift to fly faster. Flight stays within a fixed 50-unit bubble centered above the arena, with a lower limit above the floor. The camera never follows surviving teammates; spectators cannot fire or collect gems. Each death starts a 15-second countdown in host simulation time. At the deadline, the player returns beside the nearest living teammate to their death location, facing that teammate’s direction. Placement uses valid ground around the teammate, including when they are jumping; unsafe targets are skipped, and revival waits if no safe position exists. Weapon level and remaining homing reserve carry over, with shared gem progression continuing during the wait. Enemy damage is ignored for one second after revival; falling remains lethal. Spectator controls and weapon timing reset on return. Inputs are tagged with a life counter so delayed commands from before death cannot control a revived player. Disconnected players cannot respawn or anchor another player’s return. A team wipe ends the run immediately, including on a respawn deadline, and pending revivals cannot restart it. The host can return everyone to the lobby; readiness resets so everyone readies up again before the next run. If the host leaves, guests return to the lobby browser. Joining a running or full lobby is disabled.

Multiplayer cannot be paused: Escape and controller Start / Options do nothing, and the mobile timer pause target is disabled. Play until the crew dies. Keep the host browser visible and its computer awake. Browsers may require a click to recapture the mouse after switching windows, even though the game and timer start for everyone.

## Online hosting

`npm run build` produces the static game in `dist/`. `npm run serve:online` serves only that directory on localhost port 5180, with compression for scripts, meshes, styles and JSON. Publish this service through an HTTPS tunnel for a temporary playtest, or upload `dist/` to an HTTPS static host for a persistent URL. Everyone opens the resulting **internet URL**, then uses the lobby browser.

Lobby discovery uses public MQTT brokers with failover, separate room and lobby namespaces, heartbeat announcements and stale-room expiry. Ready state and start authority travel over reliable WebRTC channels; the host validates every readiness transition and will not start a public lobby with unready players. Guests cannot start the run. Ready/unready controls carry monotonic revisions; local intent updates immediately and stale roster snapshots cannot undo a newer click.

Direct internet connections use Google and Cloudflare STUN. Deployments that need relay fallback can configure `VITE_WEBRTC_ICE_SERVERS` with their own ICE server JSON before building. This is deployment configuration; players never enter network settings in the game. A TURN relay account is not bundled. Different-home NAT traversal still depends on the participating networks; testing several browser profiles on one computer does not establish compatibility with every firewall.

## Validation

- `npm test`: solo regression tests plus crew movement/deaths, shared gem credit, independent homing reserves and snapshot application.
- `npm run test:multiplayer`: four-player public lobby discovery, one-click joining, ready/unready gate, shared start, guest movement/firing and disconnect (requires a running development build and internet access).
- `npm run test:multiplayer-respawn`: respawn rules and a real WebRTC 15-second guest countdown, camera return, held-input cleanup, fresh movement/firing, host revival, repeated death, wipe and restart (requires a running development build; public discovery is stubbed).
- `npm run test:multiplayer-spectator`: spectator flow and revival with AZERTY, controller and mobile controls.
- `npm run test:multiplayer-transport`: real WebRTC input, large fragmented snapshots, epoch changes and a complete guest tap received before simulation.
- `npm run test:multiplayer-latency`: immediate predicted movement/burst/dagger jump, real WebRTC with 60 ms delay in each direction, dropped/reordered input datagrams, lost state chunks, acknowledgement recovery and epoch reset (requires internet access for the production STUN configuration).
- `npm run test:multiplayer-pause`: keyboard, controller and mobile pause prevention, focus/capture loss, controller disconnect, continuous timer and normal death (runs without internet discovery).
- `npm run test:multiplayer-responsiveness`: actual game keyboard input and rendered camera response on the next frame with 1,000 ms added RTT, plus focus-loss release recovery (requires internet lobby discovery).
- `npm run test:multiplayer-presentation`: teammate labels, remote muzzle particles without local recoil, local recoil, death visibility and cleanup.

Current scope: online cooperative survival for four players, public lobby browser, readiness, synchronized countdown, individual movement/weapons/deaths and shared gem rewards. No host migration, mid-run admission or multiplayer replay recording. Multiplayer scores remain separate from solo records.

The deterministic four-player level-IV firing benchmark in `tests/network.test.ts` measures approximately 99 KB/s of state per guest, including repair chunks, versus approximately 2.5 MB/s with escaped full-world JSON over the same two-second run. This is an empty-arena state benchmark, not a guarantee for dense endgame encounters; homing, enemies, reliable effects, input retransmission and transport headers add traffic. The network tests also cover landing/weapon-state reconciliation, independent shot randomness, lost baselines, removals, corrupted packets and fragment expiry. All players must reload the updated build before playing together.

The 1,000-enemy pose benchmark reduces steady-state enemy updates from approximately 78 KB to 15 KB per snapshot before repair chunks; health changes and removals are verified against decoded state. Browser interruptions release held guest controls while the match continues. Late releases are ignored after newer commands have been processed, critical releases remain deliverable under control-channel pressure, and run restarts discard old queued effects and baselines.
